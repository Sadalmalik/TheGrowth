## Зачем проекту архитектура

Архитектура нужна, чтобы проект мог жить: она сдерживает рост технического долга, организует
взаимодействие частей проекта и даёт управлять проектом в целом.

![[bug-hunting.png]]

Технический долг — это то, сколько дополнительного времени уходит на каждую следующую задачу.
По мере роста проекта в нём становится всё больше элементов и связей между ними, и рост
сложности ускоряется. Архитектура вводит порядок: элементы группируются по смыслу, а пути
взаимодействия между группами явно прописаны.

![[modules-grouping.png]]

*Делим по смыслу, цвету, форме.*

Для TheGrowth это особенно важно: прототип писался урывками, и в нём состояние игры, логика и
отображение перемешаны. Итог — баги, которые проявляются только в конкретных сценариях
(загрузка, переход между локациями), и страх что-либо трогать.

## Общая картина

```mermaid
flowchart TB
    subgraph Game["Game"]
        direction LR
        G1["GameFlow"] ~~~ G2["Bootstrap"] ~~~ G3["Naninovel"] ~~~ G4["Композиция интеграций"]
    end
    subgraph View["Presentation / UI"]
        direction LR
        P1["CardView"] ~~~ P2["SlotView"] ~~~ P3["Анимации карт"] ~~~ P4["Ввод, камера"] ~~~ U1["UI: слои, View, ViewModel"]
    end
    subgraph Model["Model"]
        direction LR
        M1["Карты"] ~~~ M2["Слоты"] ~~~ M3["Сюжет"] ~~~ M4["Квесты"] ~~~ M5["Крафт"] ~~~ M6["Экспедиция"] ~~~ M7["Команды"]
    end
    subgraph Core["Core"]
        direction LR
        C1["База команд"] ~~~ C2["Контент и ID"] ~~~ C3["Ядро сохранений"] ~~~ C4["Локализация"] ~~~ C5["Ядро аналитики"] ~~~ C6["Игровые сервисы"] ~~~ C7["Настройки"]
    end
    subgraph Arch["Architecture"]
        direction LR
        A1["IOC"] ~~~ A2["EventBus"] ~~~ A3["Процедурные анимации"] ~~~ A4["Утилиты"]
    end
    subgraph Integ["Integrations — сборка на модуль"]
        direction LR
        I1["Steam"] ~~~ I2["Аналитика: Amplitude, ..."] ~~~ I3["Хранилища сохранений: файлы, Web"]
    end
    Game --> View
    View --> Model
    Model --> Core
    Core --> Arch
    Game --> Integ
    Integ --> Core
    Model -.->|"ICardAnimator, события"| View
    Model -.->|"IFlowRequests, IDialogueService"| Game
```

Сплошные стрелки — зависимости (вниз; слой может использовать любой нижний). Пунктирные —
обращения наверх: только через интерфейсы, объявленные нижним слоем, и события `EventBus`.

Основная логика — в слоях. Всё, что зависит от внешнего мира (платформы, сервисы аналитики,
хранилища файлов), — модули-интеграции: каждая реализует интерфейсы из Core и подключается
в Game через DI. Кроме Game, о них никто не знает.

Ключевые идеи:

1. **Модель не знает о сцене.** Правила игры, состояние и скрипты работают без Unity-сцены
   (анимации — через интерфейсы). Это даёт автоматические тесты.
2. **Команды асинхронные, игра пошаговая.** Команда ждёт завершения действия, каждый скрипт
   завершается, сохраняемся только когда скриптов нет.
3. **Карта всегда ровно в одном слоте.** Инвентари заменены колодами.
4. **Один путь создания игры.** Новая игра и загрузка сохранения создают сессию одинаково.
5. **Состояние и сохранение разделены.** Игровые классы не знают о формате сейва; сейв — отдельные
   простые структуры с версией.
