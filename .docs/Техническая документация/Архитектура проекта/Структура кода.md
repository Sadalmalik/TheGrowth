## Модульность: что взяли и от чего отказались

В GeekyHouse проект делился на модули-пакеты с группами по уровню абстракции: модули высокого
уровня зависят от низкоуровневых, но не наоборот.

![[modules-pyramid.png]]

Принцип зависимостей «только вниз» сохраняем. Отказываемся от пакетов на каждый модуль: в
TheGrowth одна игра и маленькая команда, переиспользовать модули между проектами не нужно,
а накладные расходы на пакеты заметны.

Решение: **крупные слои — сборками (asmdef), системы — папками.**

## Слои

Схема — в [[Архитектура проекта#Общая картина]].

| Слой | Что внутри |
|---|---|
| Game | GameFlow, запуск, выбор и подключение интеграций |
| Presentation / UI | 3D-вьюхи карт и слотов, анимации, ввод, камера; UI на MVVM |
| Model | карты, слоты, сюжет, квесты, крафт, экспедиция, конкретные команды |
| Core | база команд, контент и ID, база сущности, ядро сохранений, локализация, ядро аналитики, игровые сервисы (интерфейсы), основа настроек |
| Architecture | IOC, EventBus, утилиты, процедурные анимации — как связан код, без понятий игры |
| Integrations | Steam, сервисы аналитики, хранилища сохранений под платформы — сборка на модуль |

Одна сборка на слой, папки слоёв — `Code/<Слой>/`. Не по сборке на модуль: внутри слоя
возможны перекрёстные ссылки между модулями.

Правила:
- Зависимости только вниз, циклов нет.
- Наверх — только через интерфейсы, объявленные нижним слоем (реализует верхний), и события
  `EventBus`. Пример: команда в Model ждёт анимацию через `ICardAnimator`, который объявлен в
  Model и реализован в Presentation.
- Presentation и UI друг на друга не ссылаются.
- **Model не зависит от сцены, UI и анимаций.** Это позволяет запускать игровую логику
  в тестах без Unity-сцены.
- Тип конфига живёт в слое, код которого его читает.
- Конкретные команды можно объявлять в любом слое выше Core (`MoveCamera` — Presentation,
  `StartDialogue` — Game): конфиг хранит их, не зная типа.

## Модули-интеграции

Сделано по образцу аналитики GeekyHouse:
- **ядро** в Core — только логика и интерфейсы (источники и приёмники);
- **мосты** — по классу на систему, в сборке слоя этой системы: подписываются на её события и
  передают их в ядро;
- **интеграции** — отдельные сборки, реализуют приёмники для конкретного сервиса; про них знает
  только Game.

Так же устроены игровые сервисы платформ (Steam, мобильные сторы) и хранилища сохранений
(файлы, Web). Игровые модули обязаны только публиковать события о том, что в них происходит.

## Папки

- Внутри сборки код разложен по системам: `Cards/`, `Slots/`, `Story/`, `Quests/`, `Craft/`,
  `Expedition/`, `Saves/`, `Scripting/`, ...
- Конфиги лежат в `Content/` по типам: `Cards/<Группа>/<Карта>.asset`.
- Конфиги не лежат в `Resources` — доступ через реестр контента.

## Тесты

- Основной вид — тесты логики без сцены: создать сессию, выполнить действия игрока, проверить,
  где лежат карты и что увидит игрок.
- Проверка скриптов: каждая реакция каждой карты запускается на тестовом поле.
- Проверка контента: дубли ID, битые ссылки, пропавшие типы в скриптах.
- Тесты миграций сохранений.
- Немного тестов со сценами: загрузка каждой локации, сохранение и загрузка.
