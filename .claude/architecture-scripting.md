# TheGrowth — архитектура: скрипты (команды, кондишены, эвалуаторы)

Часть детальной спецификации. Короткая версия — `CLAUDE.md` в корне.
Модель исполнения — [architecture-logic.md](architecture-logic.md).

## Решения (2026-10-11)

- Скрипты настраивают все (дизайнеры и программист). Lua не используем, C# для логики карт не
  пишем. **Развиваем систему команд.**
- Доработка системы команд обсуждается в эпике E04 (`.docs/tasks/E04 Система команд.md`).
  Решено: `Parallel`, `Background` (см. architecture-logic.md), инспектор rich-текстом, хранение —
  свой текстовый язык (ниже).
- **Уход с Odin** обязателен.

## Инспектор скриптов (вижен автора, 2026-10-11)

Скрипт рисуется не деревом полей, а многострочным rich-текстом, как редактор триггеров
Warcraft 3:

```
= if [charge > 1] and [[distance between [hero] and [target]] < 5] [+]
=   Log ["We are near target"] [-]
=   AddBuff [BuffEvaluator options] to [HeroCardEvaluator]
=   [+]
= else
=   Log ["We are too far"] [-]
=   [+]
= [+]
```

- `[...]` — кликабельный элемент: открывает небольшую панель редактирования (значение,
  переменная, вложенный эвалуатор).
- `=` — перетаскивание строки: весь скрипт — один список строк.
- `[+]` — добавить команду в блок, `[-]` — удалить команду.
- Сложные условия можно переносить на несколько строк.
- Цель — убрать визуальный шум инспектора; в связке с ИИ-агентом дизайнер описывает задачу
  словами, агент собирает скрипт.

## Формат хранения скриптов (решено 2026-10-11)

**Свой текстовый язык — источник правды.** Язык — это текст, который рисует инспектор, без
управляющих элементов (`=`, `[+]`, `[-]`, кликабельность — только в инспекторе, в файле их нет).

- Шаблон отображения команды задаётся атрибутом на классе (`Log [message]`,
  `Move [card] to [slot]`). Ключевые слова — из атрибутов, не имена классов: переименование
  класса скрипты не ломает.
- Аргументы в `[...]` — разбор однозначный: литеральные слова шаблона определяют команду, скобки —
  границы аргументов. Валидатор проверяет, что «скелеты» шаблонов не совпадают.
- Блоки — отступами, как в инспекторе.
- Ссылки на конфиги — по строковому ID.
- Хуки — именованные секции, имена — идентификаторы без пробелов, PascalCase (как события в C#):
  `OnPlaced`, `OnStep`, `OnCovered`, ...
- **Файл на карту**: логика карты — один файл рядом с ассетом карты, хуки карты — секциями.
- **Общеигровые скрипты** — отдельный файл (или несколько) с именованными хуками под точки в игре:
  кнопки UI, триггеры. Объект сцены ссылается на хук по имени (выпадающий список в инспекторе).
  Валидатор проверяет, что все ссылки на хуки существуют.
- Импортёр (`ScriptedImporter`) разбирает файл при импорте, ошибки — с номером строки.
- Расширения: `.script` и `.dialog` (см. «Синтаксис языка»).

```
OnPlaced:
    if [charge > 1] and [[distance between [hero] and [target]] < 5]
        log "We are near target"
        AddBuff poison to [hero]
    else
        log "We are too far"

OnStep:
    Parallel
        Move [active card] to [nearest free slot]
        Flip [card under [active card]]
```

### Шаблоны команд: атрибут `[Script]` (решено 2026-10-11)

Имя и синтаксис команды (кондишена, эвалуатора) задаются атрибутом на классе. Имя класса ни на что
не влияет — переименование не ломает скрипты.

```csharp
[Script("if", "if [Condition] {OnTrue} else {OnFalse}")]
public class Branch : Command
{
    public Condition Condition = new And();
    public List<Command> OnTrue = new List<Command>();
    public List<Command> OnFalse = new List<Command>();
}

[Script("log", "log [Message]")]
public class DebugLog : Command
{
    public string Message;
}
```

- Первый аргумент — имя: стабильный ключ для списка команд в инспекторе, каталога для ИИ и
  документации.
- `[Field]` — параметр; в тексте кликабелен.
- `{Field}` — список вложенных команд (блок). `{}`, а не `<>`: угловые скобки конфликтуют со
  сравнениями в шаблонах (`[A] < [B]`).
- Обе скобки существуют только в шаблонах. В файле блоков не видно — только отступы.

Многострочные команды:
- Маркер блока всегда означает перенос строки, блок с отступом, снова перенос.
- Текст до первого блока — заголовок; текст между блоками — строки-продолжения на отступе
  заголовка (`else`); текст после последнего блока — замыкающая строка
  (`repeat {Body} until [Condition]`).
- Пропуски: продолжение без параметров с пустым блоком не выводится (`if` без `else`). Инспектор
  показывает скрытую секцию кнопкой (`[+ else]`).
- Разбор: строка на том же отступе, совпадающая с текстом продолжения, относится к предыдущей
  команде; не совпадает — секция пустая.

```
if [charge > 1]
    log "near"
else
    log "far"
```

Валидатор при запуске:
- имена уникальны;
- «скелеты» шаблонов (литеральные слова + места параметров) не совпадают;
- слова продолжений (`else`) не начинают ни одну другую команду;
- поля из `[..]` и `{..}` существуют, `{..}` — список команд.

Открыто (`.docs/Вопросы.md`): повторяющиеся секции (`else if`); скобки у литералов внутри
вложенного узла.

### Синтаксис языка (решено 2026-10-17)

- **Файлы:** `.script` — скрипты карт и общеигровые хуки, `.dialog` — диалоги. UTF-8.
- **Секции:** строка с нулевым отступом вида `Имя:`, после двоеточия ничего нет. Всё содержимое
  секции — с отступом. Реплика `Lucia: текст` всегда внутри секции, поэтому с заголовком не путается.
- **Свойства-выражения** (в файле карты): строка с нулевым отступом `Имя -> [выражение]`, например
  `AllowedMoves -> [slots around [active card] cross 1]` (решено 2026-10-17; реализация — T059).
- **Отступы:** парсер принимает любую постоянную ширину (блок глубже родителя и одинаков внутри
  себя), табуляция — ошибка. Принтер пишет 4 пробела — ширина задаётся одной константой.
- **Скобки — только вокруг вложенных узлов** (эвалуаторов, условий). Литералы — без скобок:
  числа, строки в кавычках, `true` / `false`, значения enum, ID конфигов, ссылки на секции,
  переменные `$имя`. Литерал в параметре типа `Evaluator<T>` оборачивается в константу.
  Приоритета операций нет: `[[$a + 1] > 3]`. Кликабельность в инспекторе от скобок не зависит.

```
if [$trust_lucia > 3]
    add 5 to $coins
    move [active card] to [nearest free slot]
    log "We are near target"
```

- **Списки** в параметре — элементы через запятую.
- **Текст до конца строки:** `[Field...]` в шаблоне — только последний параметр строки, забирает
  остаток строки до ID `#xxxxxx`, если он есть.
- **Несколько шаблонов у класса:** `[Script]` можно повесить несколько раз (`Lucia: текст` и
  `Lucia.happy: текст` — один класс). Принтер выбирает самый подробный шаблон, у которого
  заполнены все параметры.
- **Комментарии:** строка `// ...` — пустая команда в дереве, переживает пересохранение. В конце
  строки после кода комментариев нет.
- **`else if`** — вложенный `if` внутри `else`.
- Ошибки разбора собираются по всему файлу, с номерами строк.
- Принтер — канонический формат (пустая строка между секциями). Тест на каждую команду:
  печать → разбор → печать даёт тот же текст.

### Реализация (T056, `Code/Core/Scripting/Registry`, `Language`, `Text`)

- `ScriptRegistry` (не статический) собирает классы с `[Script]`, проверяет шаблоны и при ошибках
  бросает одно исключение со списком всех проблем. Тестовые сборки в общий реестр не попадают.
- `ScriptParser` / `ScriptPrinter`; ширина отступа — `ScriptSyntax.IndentWidth`.
- `LineId` — свойство команды (как `Location`), только на первой строке команды.
- Незаданный параметр печатается как `[]` — такой текст не разбирается, место видно сразу.
- `$имя` — только в параметрах-узлах (`Condition`, `Evaluator<T>`).
- Комментарий с нулевым отступом — ошибка.
- Ограничения на имена: ID файла скриптов — идентификатор (без пробелов, не с цифры), иначе на него
  нельзя сослаться; ID персонажа не должен совпадать с ключевым словом команды (иначе реплика
  `Имя: текст` неоднозначна). Проверяет валидатор.
- Импортёр `.script` / `.dialog` (`Code/Editor/Scripting/`): ID конфигов — по реестру контента
  (переимпорт при изменении набора ID через зависимость `TheGrowth/ContentIds`); без реестра —
  разрешающая заглушка с предупреждением. Переменные — заглушка до T052.
- Параметр-конфиг команды — наследник `ContentAsset`.
- `ScriptLanguage` — глобальный сервис с реестром команд; `ContentScriptLibrary` — система
  сессии, разбирает файлы скриптов по запросу и кеширует на сессию (T060).
- Доработки — T059.

### Типы файлов и контексты команд (решено 2026-10-17)

- Файлы скриптов (карты, общеигровые хуки) и файлы диалогов — разные расширения.
- У команды — контекст: везде / только в диалогах / только вне диалогов. Валидатор проверяет по
  типу файла. Таблица контекстов — в architecture-dialogs.md.

Для ИИ:
- каталог команд (шаблоны, типы параметров, описания) генерируется из атрибутов в скилл
  `.claude/skills/`;
- обратная связь: ИИ пишет файл → Unity переимпортирует → ошибки в консоли → ИИ читает их через
  MCP. MCP — для проверки и прогона, не для хранения; можно добавить позже.

Отклонённые варианты: `[SerializeReference]` + CLI/MCP (ИИ правит только при открытом редакторе,
merge YAML с `rid` не разрешить руками), JSON со схемой (многословно, две формы представления).

## База команд (решено 2026-10-17)

- Асинхронный примитив — **UniTask** (Cysharp): работает в Web, есть `WhenAll`, интеграция с
  DOTween, окно TaskTracker. Копия UniTask внутри Naninovel — в своём namespace, не конфликтует.
- Асинхронны только **команды**: `UniTask Execute(ScriptContext)`. Мгновенные команды наследуют
  `InstantCommand` (`void Run(ScriptContext)`). **Кондишены и эвалуаторы синхронны.**
- `ScriptContext` — развитие `Context` прототипа: цепочка родителей с типизированными данными
  (`ActiveCard`, `IteratingCard`, ...; дочерний — `context.With(data)`), системы сессии через
  `context.Get<T>()`, текущий запуск и его токен отмены. Корневой контекст — на сессию;
  `Game.BaseContext` нет.
- `ScriptRunner` (система сессии): каждый запуск (хук карты, общеигровой хук, диалог) —
  зарегистрированный `ScriptExecution`. Вложенные реакции карт — внутри того же запуска.
  `Background` — отдельный запуск, токен связан с токеном scope, а не родителя. `Parallel` —
  `UniTask.WhenAll`. Команды ожидания игрока (реплика, выбор, ввод) оборачивают ожидание в
  `context.WaitForPlayer()`; `IsIdle` = активных запусков нет или все ждут игрока.
- Ошибка в команде — лог с файлом и строкой скрипта, запуск прерывается, игра продолжается.
  Отмена — тихая.
- **Скрипты разбираются из текста при загрузке** (с кешем), в редакторе — ещё и при импорте для
  проверки. Парсер — в Core, работает в билде. Команды — обычные классы: `[SerializeReference]`
  и `[Serializable]` им не нужны.

```csharp
public abstract class Command
{
    public abstract UniTask Execute(ScriptContext context);
}

public abstract class InstantCommand : Command
{
    public sealed override UniTask Execute(ScriptContext context)
    {
        Run(context);
        return UniTask.CompletedTask;
    }

    protected abstract void Run(ScriptContext context);
}

public abstract class Condition
{
    public abstract bool Check(ScriptContext context);
}

public abstract class Evaluator<T>
{
    public abstract T Evaluate(ScriptContext context);
}
```

## Исполнитель и управляющие команды (решено 2026-10-17)

Управляющие конструкции исполняет сам `ScriptRunner` по явному стеку кадров, а не C#-рекурсия:
асинхронный метод нельзя сохранить посреди выполнения, а стек кадров — данные.

- **Обычные команды** — `UniTask Execute(ScriptContext)`, подавляющее большинство.
- **Управляющие команды** (`if`, `choice` / `option`, `goto`, `call`, `return`) свои блоки не
  выполняют, а возвращают шаг исполнителю:

```csharp
public abstract class ControlCommand : Command
{
    // Enter(block) | Jump(section) | Call(section) | Return
    public abstract UniTask<ControlStep> Next(ScriptContext context);
}

[Script("if", "if [Condition] {OnTrue} else {OnFalse}")]
public class Branch : ControlCommand
{
    public Condition Condition;
    public List<Command> OnTrue;
    public List<Command> OnFalse;

    public override UniTask<ControlStep> Next(ScriptContext context)
        => UniTask.FromResult(ControlStep.Enter(Condition.Check(context) ? OnTrue : OnFalse));
}
```

- Кадр: файл, секция, блок, индекс команды; стек `call` — часть стека кадров. `goto` снимает
  кадры текущей секции и кладёт кадр целевой; `call` кладёт кадр с возвратом; `return` снимает.
- `choice` — управляющая команда с ожиданием игрока: показывает варианты, ждёт выбора, возвращает
  `Enter(тело варианта)`.
- `Parallel`, `Background`, циклы (`for each card`) — обычные команды; свои блоки запускают как
  вложенные запуски (`context.Runner.RunBlock(...)`). Позиция внутри них не сохраняется — в
  диалогах команды ожидания внутри них запрещены (валидатор).
- Реакции карт — вложенные запуски изнутри обычных команд.
- Один исполнитель для всех файлов (скрипты и диалоги).
- Реализация (T054, `Code/Core/Scripting/`): `goto` внутри `call` сохраняет кадр вызова — после
  целевой секции исполнение возвращается к вызвавшему (как `jump` в Ren'Py). `ControlCommand`
  объявляет свои блоки (`BlockCount` / `GetBlock`) — по ним строится путь позиции. Во вложенных
  ветках (`parallel`, `RunSection`) `goto` / `return` действуют в пределах ветки.
- Известные ограничения: ожидание игрока учитывается на весь запуск (если одна ветка `parallel`
  ждёт игрока, а другая анимируется, запуск считается ждущим — в диалогах это закрыто запретом
  ожидания внутри `parallel`); долгие команды обязаны слушать `context.Cancellation`, иначе при
  ошибке соседней ветки `parallel` остаётся «хвост».
- Плюсы: `goto` / `call` без раскрутки исключениями, точная позиция в ошибках и для подсветки
  строки в инспекторе, позиция исполнения сериализуема.

## Почему ломались скрипты карт

54 файла (конфиги, префабы, все сцены) сериализованы Odin с `SerializedFormat: 0` — бинарный
блоб внутри YAML с полными именами типов (`XandArt.TheGrowth.Common.Random`1[[...SlotEntity, Code]], Code`).
Переименование класса, перенос namespace или сборки теряет данные. GUID ассетов ни при чём.

## `[SerializeReference]` — для остальных полиморфных конфигов

Скрипты хранятся текстом. `[SerializeReference]` остаётся для прочих полиморфных данных в
конфигах — например, список компонентов карты.

- `[SerializeReference] List<ICardSettings>` — список разнотипных объектов. Стандартный инспектор
  не умеет добавлять элемент с выбором типа → нужен drawer с выбором типа (или Odin как drawer).
- Кастомный инспектор для отдельного класса возможен: drawer выбора типа делегирует отрисовку
  drawer'у конкретного типа. Подбирает ли Unity 6 drawer по конкретному типу сам — проверить.
- Ограничения: тип значения `[Serializable]`, не абстрактный, не `UnityEngine.Object`; generic-типы
  поддерживаются (Unity 2023.1+); каждое вложенное полиморфное поле тоже `[SerializeReference]`;
  `Dictionary`/`HashSet` не сериализуются; переименования — `[MovedFrom]`; данные пропавших типов
  сохраняются (валидатор: `SerializationUtility.HasManagedReferencesWithMissingTypes`).
- Ловушка: дублирование элемента списка в инспекторе копирует ссылку, а не объект.

## План миграции с Odin

1. Пока классы на Odin — выгрузить все скриптовые данные общим reflection-дампером
   (объекты — POCO). Ключ: GUID ассета / сцена + путь объекта, путь поля.
2. Скрипты карт и шагов сюжета → принтер → текстовые файлы на новом языке. Скрипты кнопок и
   прочих объектов сцен → хуки в общеигровых файлах + ссылки на хуки.
3. Прочие полиморфные конфиги — на Unity-сериализацию (`SerializedScriptableObject` →
   `ScriptableObject`, `SerializedMonoBehaviour` → `MonoBehaviour`, `[SerializeReference]`).
4. Проверка: разбор новых файлов и сравнение деревьев с выгрузкой.
5. Удаление Odin.
