# TheGrowth — архитектура: модель данных, карты, слоты, сохранения

Часть детальной спецификации. Короткая версия — `CLAUDE.md` в корне.
Статус: согласовано в обсуждении 2026-10-10 (выбран вариант «системы + DTO»), кода ещё нет.

## Решение и причины

Отказываемся от прототипного подхода «всё состояние — entity с компонентами, сериализуемые напрямую через Newtonsoft». Причины (по коду прототипа):
- `TypeNameHandling.All` пишет в сейв полные имена .NET-типов → переименование класса или namespace после релиза ломает сейвы игроков.
- Каждый runtime-класс обязан быть сохраняемым: `[JsonProperty]`/`[JsonIgnore]`, хуки
  `OnPreSave`/`OnPostLoad`, `Ref<T>` со статическим резолвом. Одна забытая аннотация
  (`EntityComponent.Owner`) ломает весь сейв.
- DTO уже фактически есть, но встроены в entity и синхронизируются руками
  (`SlotEntity._cards` + `_cardsList`, `BoardEntity._slots` + `Slots`).
- Поиск по общему списку entity перебором (`QuestManager` каждый кадр).

Выбранный подход близок к GeekyHouse (менеджеры/системы + отдельные save-объекты), с поправками: слоты сохранений вместо одного глобального сейва, пересоздаваемая сессия, один архив на слот, никакого runtime-состояния в ScriptableObject, никаких Dirty-флагов.

## Три вида данных

| Вид | Где живёт | Кто меняет | Примеры |
|---|---|---|---|
| Статика (конфиги) | ScriptableObject | только редактор | `CardModel`, `LocationModel`, `StoryStep`, `DeckModel`, `CraftModel`, `SlotModel` |
| Runtime-состояние | обычные C# классы, принадлежат системе сессии | системы модели | `CardInstance`, `Slot`, `StoryState`, `QuestLog`, `Flags`, `ExpeditionState` |
| Сохранение | плоские DTO с версией | только `ISaveable.Write/Read` | `CardSave`, `SlotSave`, `StorySave`, `ExpeditionSave`, `SaveMeta` |

Инварианты:
- Runtime-классы не содержат атрибутов сериализации и не знают о JSON.
- DTO не содержат логики и ссылок на runtime-объекты — только примитивы, ID и вложенные DTO.
- ScriptableObject не хранит runtime-состояние (ошибка GeekyHouse: `GameResourceLogic.Amount`).

## Конфиги и стабильные ID

Решено 2026-10-11: у конфигов — строковые ID, у объектов внутри игры (экземпляры карт) — `int`.

- У каждого конфига, на который ссылаются сохранения или скрипты, есть строковый `Id`
  (например, `monster_1`). Уникален в пределах типа: тип однозначно задан полем.
- `Id` — поле ассета, а не имя файла: переименование ассета ID не меняет. По умолчанию
  заполняется из имени при создании.
- Ссылка в DTO и в тексте скрипта — строковый ID. Ссылка в runtime — прямая ссылка на ScriptableObject.
- Реализация (T060, `Code/Core/Content/`): базовый класс конфигов `ContentAsset` с полем `Id`;
  `IContentRegistry` в глобальном контейнере; реестр — плоский отсортированный список конфигов +
  список файлов скриптов (`.script` / `.dialog`, ID = имя файла). Область уникальности ID —
  прямой наследник `ContentAsset` (поиск идёт и по базовым типам). Пустой ID заполняется из имени
  при сборке реестра. Автосборка при изменении конфигов, проверка перед билдом, меню
  `[TheGrowth]/Content/Rebuild Registry` и `Validate`.
- `ContentRegistry` (ScriptableObject, собирается редактор-тулзой) хранит списки всех конфигов по
  типам. Заменяет `Resources.LoadAll` в `AssetGuidsManager`. Резолв: `registry.Get<CardModel>(id)`.
- Валидатор (меню + pre-build hook): дубли ID, конфиги вне реестра, битые ссылки → ошибка.
- Объекты внутри игры (экземпляры карт) получают `int InstanceId` из счётчика сессии;
  счётчик сохраняется.

## Сущности: карта (Model — Instance — Save)

Понятие entity сохраняется только там, где у объекта есть идентичность и он участвует в
правилах: **экземпляр карты**. Схема — как модуль Game Entity в GeekyHouse:

```
CardModel (SO)                 CardInstance (runtime)           CardSave (DTO)
  Id, визуал, тип       ──►      InstanceId, Model,      ──►      instanceId, modelId,
  [SerializeReference]           SlotId, Index, IsFaceUp          slot, index, faceUp,
  List<ICardSettings>            List<CardBehaviour>              components: { key → dto }
    Settings ──────────────────►   Behaviour ─────────────────►     Data
```

- `ICardSettings` (в конфиге) создаёт `CardBehaviour` (runtime). Поведение может иметь своё
  состояние и свой DTO.
- Ключ компонента в сейве — стабильная строка из атрибута (`[CardComponentKey("charges")]`), не имя
  типа. Переименование класса сейв не ломает.
- Логика поведения (реакции на события) задаётся скриптами — см. architecture-scripting.md.
  Поведение хранит только данные и даёт API.
- Позиция в мире (`Vector3`) не является частью модели. Модель знает только слот и индекс.
- `CardRegistry` — система сессии: создание, уничтожение, поиск по `InstanceId`.

### Сущности: композиция (решено 2026-10-18)

- **Одна `Entity` с компонентами**, без `CompositeEntity` и иерархии наследования. Вид сущности
  определяется конфигом и набором компонентов.
- Виды: **`Card`** — лежит в слоте поля; **`Mechanic`** — объект механики в слоте связи (стена,
  телепорт); **`Modifier`** — модификатор на карте или на объекте механики (по сути статус, своя вьюха). До 2026-11-04 назывался `Cover`; переименован, чтобы не путать с хуками `OnCovered` / `OnUnCovered` (карта легла на карту).
- Общее у всех: ID, конфиг, теги, переменные, компоненты, место (слот поля, слот связи или
  сущность-владелец).
- **Конфиг — единый `Model`** с пресетами создания в меню Create (Card, Modifier, Mechanic): пресет
  добавляет нужные компоненты (у карты — `CardBrain`), их нельзя удалить в инспекторе.
- **Вид в конфиге** (решено 2026-10-18): у `Model` поле `Kind` (Card / Modifier / Mechanic).
  Обязательные компоненты вида описаны в коде в одном месте; инспектор блокирует их удаление по
  этому описанию; валидатор добавляет недостающие во все конфиги вида, если описание изменилось.
- **Типизированные ссылки:** атрибут `[ModelKind(Card)]` на поле — инспектор предлагает только
  конфиги этого вида, валидатор и парсер скриптов проверяют вид. У всех `Model` одно пространство
  ID (ID карты и модификатора не совпадают).
- **Вьюхи — не компоненты сущности.** Настройки визуала — компонент конфига (связывание через
  конфиги), вьюху создаёт Presentation по сущности и её конфигу. Модель работает без сцены.
- Для удобного кода — типизированные обёртки (`card.Brain` вместо `entity.GetRequired<CardBrain>()`).
- Имя класса конфига — **`EntityModel`** (2026-10-23): `Model` конфликтует с namespace `TheGrowth.Model`.
  Схема карты: `EntityModel` (вид Card) → `Entity` → DTO сейва сущности.
- **Теги** (2026-10-23) — только из конфига, во время игры не меняются (пока). Изменяемое состояние —
  переменные и модификаторы.
- **Имена тегов** (2026-11-04) — CamelCase: с заглавной буквы, только буквы и цифры (`PlayerSpawn`,
  `Exit`, `Monster`); проверяет `TagCatalog`. Реестр общий для карт и слотов; смысл тега зависит от
  того, на чём он стоит: `Exit` на слоте — сюда можно положить карту выхода, на карте — это карта
  выхода. Отдельных тегов для карты и слота с тем же смыслом не заводим.
- **Инвентарь игрока** (2026-10-23) — одна колода: слот сессии `hub/inventory`. Он существует всегда, пока
  есть сессия, не привязан к сцене и доступен из любой локации и любой системы через `SlotSystem`;
  сцена хаба только показывает его вьюхой. «Колода» — это слот с правилами колоды, а не предмет в слоте. Для просмотра — отдельный режим, который листает
  колоду, группируя карты по тегам и другим параметрам (возможно, позже — отдельные типы).

### Реализация сущностей (T073, 2026-10-23)

Код: `Code/Core/Entities/` (база), `Code/Model/Entities/` (`CardBrain`, `RequiredComponents`,
`EntityRegistry`), `Code/Editor/Entities/` (пресеты `Create/[Game]/Entity/Card|Modifier|Mechanic`,
инспектор `EntityModelEditor` без Odin, `ModelKindDrawer`, проверки). Примеры — `Content/Entities/`
(Hero, Monster с `charges = 3`, Herb, Exit, Poison — модификатор, Wall — объект механики).

- Компонент: `ComponentSettings<TBehaviour>` в списке `[SerializeReference]` конфига →
  `ComponentBehaviour<TSettings, TState>`; ключ — `[ComponentKey("card_brain")]` на классе настроек
  (`^[a-z][a-z0-9_]*$`), не больше одного компонента на ключ; без ключа или с повтором компонент
  не создаётся (ошибка валидатора). Версии DTO у компонента нет — миграции на уровне секции
  `entities`.
- `CardBrain` (Model) — пока только «лицом вверх / рубашкой». Обязательные компоненты —
  `RequiredComponents` (Model); дописываются в `ContentRegistryBuilder.Rebuild` (импорт, меню,
  перед билдом), в начало списка; конфиг с пропавшими типами компонентов не трогается. Удаление
  обязательного в инспекторе заблокировано; смена вида дописывает обязательные нового вида.
- Место и жизнь сущности знает реестр: `Entity` читает `Owner`, `Modifiers`, `IsDestroyed` через
  `IEntityRegistry`; слот карты знает только `SlotSystem` (`GetSlot(entity)`).
- Переменные сущности: пустое значение в конфиге — значение из объявления; запись переменной,
  которой нет у конфига, — ошибка исполнения с местом; `VariableStore` получил схему владельца.
- `[ModelKind]` — через общий механизм ограничений параметров `IScriptValueFilter` (проверка после
  разбора, у списков — каждый элемент); валидатор обходит сериализуемые поля конфигов, включая
  вложенные и `[SerializeReference]`.
- `entities` (`LoadOrder` 10): `{nextId, entities: [{id, model, variables, components: {ключ: DTO},
  modifiers: [...]}]}` — модификаторы вложены во владельца; модификаторов на модификаторах нет.
- Аномалии загрузки: сущность в двух слотах — ошибка, остаётся в первом; карта или объект
  механики без слота — уничтожается; неизвестный слот или конфиг, вид не подходит месту — не
  восстанавливается; ID пропущенных сущностей повторно не выдаются.

### Модель карты (решено 2026-10-17)

| | CardModel (конфиг) | CardInstance (в игре) | CardSave (сейв) |
|---|---|---|---|
| Идентичность | строковый `Id` | `int InstanceId` + ссылка на модель | `instanceId`, `modelId` |
| Тексты | имя, описание (локализуемые) | — | — |
| Теги | список тегов из реестра | — | — |
| Место | — | слот + индекс, лицом вверх или нет | `slot`, `index`, `faceUp` |
| Переменные | выбраны из реестра + значения по умолчанию | текущие значения | `{ имя: значение }` |
| Компоненты | `[SerializeReference] List<ICardSettings>` | поведения | `{ ключ: DTO }` |
| Логика | файл `.script` рядом с ассетом | — | — |

- **Логика карты — в её файле `.script`:** хуки секциями и свойства-выражения строками с нулевым
  отступом через `->` (не `=`, чтобы не путать с математикой):

```
AllowedMoves -> [slots around [active card] cross 1]
SpawnSlot -> [random [free table slots]]

OnStep:
    ...
```

- **Хуки карты** — все шесть: `OnPlacedFirstTime`, `OnPlaced`, `OnFlipped`, `OnStep`, `OnCovered`,
  `OnUnCovered`. Новые — по мере надобности, с ГД. `OnCovered` / `OnUnCovered` — карта легла на карту
  в том же слоте / ушла с неё. Хуки размещения — только в слотах с `InvokePlaceEvent` (клетки поля).
  Смысл, порядок, базовый набор узлов — architecture-scripting.md, «Скрипты карт» (2026-11-04).
- **Общие куски логики** — секции в общих `.script`-файлах, карта вызывает их через
  `call Monsters.CrossMovement` (замена `ExecuteCommandConfig` прототипа).
- **Теги вместо групп.** Группы-списки прототипа (`CardGroups`) убираются. У карты — теги из
  реестра; в скриптах `[card] has tag monster`. Вид карты (герой, способность, ресурс, монстр,
  особая) — тоже тег. Где от вида зависит C#-код (правила героя) — компонент (`HeroSettings`),
  не enum.
- **Герой**: персонаж (конфиг для диалогов: портреты, Spine, эмоции), карта героя и карты
  способностей — отдельные конфиги. Карта героя ссылается на персонажа. У персонажа может быть
  несколько способностей; способность связана с героем компонентом (как `AbilityOwner`), возможно
  позже — прямо с персонажем.
- **Герой и способности, шаг 6 E03** (решено 2026-11-04, T075):
  - персонаж — пока минимальный конфиг: ID, имя; портреты, Spine, эмоции — с диалогами (E12);
  - карта героя — компонент со ссылкой на персонажа; тег `Hero` остаётся для скриптов;
  - карта способности — компонент со ссылкой на персонажа-владельца; без владельца — способность
    игрока, подходит любому герою;
  - раскладка кладёт способности в руку экспедиции; способность чужого персонажа или больше ёмкости
    руки — ошибка до изменений;
  - розыгрыш способности (игрок кладёт карту на клетку из её `AllowedMoves`) — шаг 7, вместе с ходом
    героя; заканчивает ли он ход — решает скрипт способности, жёсткой привязки в коде нет.
- **Ёмкость слотов** (2026-11-04) — настраивается в конфиге, не константами в коде (баланс): инвентарь
  хаба — без лимита, рука экспедиции — 3 карты; карта героя для старта экспедиции обязательна.
- Реализация (T075, 2026-11-04), код — `Code/Model/Heroes/`, `Code/Model/Slots/SlotsConfig.cs`,
  `Code/Editor/Heroes/HeroChecks.cs`:
  - `CharacterModel` (`ContentAsset`, меню `[Game]/Character`) — ID и имя строкой (`DisplayName`; `m_Name` занят
    Unity). Примеры — `Content/Characters/` (Lucia, Alfredo, Stefan).
  - Карта героя — компонент `HeroCardSettings` → `HeroCard` (ключ `hero_card`, ссылка на персонажа, состояния нет);
    тег — `HeroCardSettings.Tag` (`Hero`). Способность — `AbilityCardSettings` → `AbilityCard` (ключ `ability_card`,
    владелец; пусто — способность игрока); `AbilityCard.Fits(hero)` — владельца нет или он равен персонажу `HeroCard`
    героя (карте без компонента героя подходят только способности игрока). Заряды — переменная `charges`.
  - Валидатор (`ContentErrorKind.InvalidHero`): компонент героя или способности не у карты, у героя нет персонажа —
    ошибка; компонент героя без тега `Hero`, тег без компонента — предупреждение. Пример шага 5 `Content/Entities/Hero.asset`
    (тег без компонента) давал предупреждение — удалён в T076.
  - `SlotsConfig` (`ContentAsset`, меню `[Game]/Slots Config`, `Content/Slots/SlotsConfig.asset`) — ёмкость инвентаря
    (0 — без лимита) и руки (3); один на проект (как `FieldConfig`: несколько — ошибка, ни одного в полном реестре —
    ошибка `InvalidSlotsConfig`). `SlotSystem` читает первый конфиг реестра в `Init` (`InventoryRules`, `HandRules` —
    свойства экземпляра); конфига нет — значения по умолчанию конфига. Остальные служебные слоты — без лимита.
  - Полный слот: `Slot.IsFull`, условие `[Slot] is full`; `move` (карта не из этого слота) и `create` в полный слот ничего не
    делают и пишут предупреждение `[Cards] <файл:строка>: ... is full (N), the command does nothing`; `SlotSystem.Move` /
    `Create` по-прежнему бросают исключение.
  - Карты героев — `Content/Entities/Heroes/` (Lucia, Alfredo — крест на 1 без монстров, препятствий и пустых; Stefan —
    ромб на 1 без пустых; раскрытие вокруг (квадрат 1, как в прототипе) и под собой — общий `Content/Scripts/Cards.script`,
    `RevealAround`).
    Способности — `Content/Entities/Abilities/` (владельцы и заряды из прототипа: Vision — Lucia, 4; Revolver — Stefan, 2;
    Teleport — игрока, 2; Confuse — Lucia, 3; Talisman — игрока, 1), расход заряда — `Content/Scripts/Abilities.script`,
    `Spend` (заряды есть — в руку, нет — в рюкзак рубашкой вверх). Части хода — строки-комментарии (шаг 7; заменены узлами в
    T076).
- **Визуал карты** (портрет, декор, какую переменную показывать счётчиком) — компонент слоя
  Presentation в списке компонентов (связывание через конфиги).
- `Charges` → переменная `charges` из реестра.
- Баффов и RPG-механик нет — игра строится на механиках карт.

## Слоты: карта всегда ровно в одном месте

Вижен команды: игра полностью трёхмерная, инвентари заменяются колодами, UI крафта — доской со
слотами. Термин — **слот** (решено 2026-10-11, вместо «зоны»).

- **Слот** — место, на которое можно положить одну или несколько карт: колода героев в хабе,
  колода ресурсов, слот доски крафта, клетка поля экспедиции, рука, колода экспедиции, сброс,
  рюкзак. Применимо и к выбору карт, и к инвентарю.
- Карта находится ровно в одном слоте. Перемещение — атомарная операция `SlotSystem.Move(card,
  toSlot, index)`: убрать из старого, добавить в новый, записать событие. Нет
  `CardInventoryComponent` и ссылок «карта знает свой инвентарь, инвентарь знает карту».
- Модель слота: упорядоченный список карт + правила (`SlotRules`: фильтр допустимых карт,
  ёмкость, рубашкой/лицом). Правила задаются в `SlotModel` или генерируются (клетки поля).
- Раскладка карт в слоте (стопка, веер руки, растягивание вдоль кривой) — забота вьюхи
  (`SlotView`), не модели.
- ID слота — стабильный строковый ключ, читаемый в сейве и отладке: `hub/heroes`,
  `hub/resources`, `craft/<craftId>/2`, `exp/board/3,4`, `exp/hand`, `exp/deck`,
  `exp/discard`, `exp/backpack`.
- Поле экспедиции — граф слотов (см. «Поле — граф слотов»).
- Реализация (T073, 2026-10-23): `Code/Model/Slots/` — `SlotSystem` (секция `slots`, `LoadOrder` 20,

### Поле — граф слотов (решено 2026-10-18, T057)

- Поле — граф из слотов и связей (явные связи). Из графа строится квадратная или гексагональная
  сетка или произвольное поле. Целочисленных координат нет; уникальные слоты — по тегам
  (`PlayerSpawn`).
- У слотов и связей стабильные уникальные ID (для сейвов и скриптов).
- **Связи ненаправленные.** У связи есть слот, в него ставится объект механики (стена, телепорт и
  т.п.; название — открытый вопрос). Проходимость проверяют сами объекты на связях.
- В слоте поля лежат карты (несколько); отдельные модификаторы слотов не нужны. **Модификаторы** — на
  картах и на объектах механики; модификатор по сути — статус, у него своя вьюха.
- **Две меры близости**, дизайнеры комбинируют их операциями над наборами:
  - геометрия — фигуры (`IShape`: круг, прямоугольник, произвольные) с позицией и размером,
    проверка «точка внутри»; постоянные фигуры, нарисованные на поле, — дополнение к тегам;
    набор фигур и единицы — architecture-scripting.md, «Фигуры» (2026-11-04; реализация T075 — `Shape` без позиции,
    `Code/Model/Shapes/`, клетки в фигуре — `FieldSlots.GetCellsIn` по позициям слотов графа);
  - граф — достижимость за N связей, поиск пути A* (монстры обходят стены).
- Направления («крестом», «к цели») — по геометрии связей (вектор между позициями слотов).
- Инструмент редактирования поля — простой и универсальный, обсудить при реализации (подход
  TotalShooter не копировать — неудобен).
- Структура поля во время игры не меняется (решено 2026-10-21): в сейве только содержимое слотов
  и объекты механики, не слоты и связи.

#### Редактор поля (решено 2026-10-21)

- Граф хранится в конфиге рядом со сценой локации. На сцене — компонент `Graph`, ссылается на
  конфиг и рисует гизмо слотов и связей.
- Своя панель инструментов в Scene View; Esc сбрасывает активный инструмент:
  - **Выбор** — выбрать слот или связь; в инспекторе `Graph` — параметры выбранного: теги,
    конфиги объектов механики, которые туда встают (необязательно).
  - **Single** — клик по геометрии сцены ставит слот; Ctrl+клик по слоту удаляет его со всеми связями.
  - **Grid** — дополнительная панель настроек: тип (Square / Hex), расстояние между ячейками.
    Первый клик по геометрии — начало «натягивания»: от начальной точки до мыши строится сетка;
    второй клик фиксирует её и добавляет к графу.
  - **Связи** — первый клик по слоту тянет линию до мыши, клик по другому слоту создаёт связь.
  - **Автоконнект** (чекбокс + радиус) — новые слоты сами соединяются с ближайшими слотами.
  - **Минимальный радиус** между слотами.
- Уточнения (2026-10-21):
  - на конфиг графа ссылается и `LocationModel` (модель строит поле без сцены): инструмент сам
    записывает конфиг из `Graph` в `LocationModel` этой сцены, валидатор локаций (T063) проверяет
    совпадение;
  - позиции слотов хранятся 3D-точками в локальных координатах `Graph`; как считать фигуры,
    расстояния и направления — решим вместе с эвалуаторами (E03);
  - сетка — явная группа в конфиге: тип, шаг, натянута от A до B, слоты принадлежат ей; группу
    можно выбрать и удалить целиком; перенастройки нет (удалить и натянуть заново);
  - связи в сетке: квадратная — 4 соседа крестом, галка «диагонали» — 8; гекс — 6 соседей,
    ориентация (вершиной или гранью вверх) — на панели сетки;
  - в «Выборе» слот двигается ручкой с учётом минимального радиуса; множественный выбор — позже;
  - Ctrl+клик по связи в инструменте связей удаляет её; связь к уже связанному слоту не создаётся;
  - автоконнект соединяет новый слот со всеми слотами в радиусе; у новой сетки — крайние клетки с
    существующими слотами; слот ближе минимального радиуса не ставится, клетки сетки на месте
    существующих слотов пропускаются;
  - режим **Tags** (кисть тегов, решено 2026-10-22, T071) — после Links: ползунок размера кисти и
    текущий тег; круг кисти под мышью; ЛКМ — добавить тег слотам в кисти, Shift+ЛКМ — убрать;
    радиус — в локальных единицах `Graph` (круг), слот в кисти — центр в радиусе по XZ;
  - отмена (Ctrl+Z) для всех правок; ID слотов и связей — автоматические, уникальные;
  - теги слотов — из общего реестра тегов (тот же, что у карт); минимальный реестр — вместе с
    редактором, карты подключатся в E03;
  - поле «объект механики» у слотов и связей — в E03, когда появится `Model` вида `Mechanic`.

- Доработки (решено 2026-10-22, T070):
  - размер карты в 3D — глобальная настройка (по умолчанию 1,5 × 2: x = 1,5, z = 2), конфиг
    настроек поля в Model, один на проект, в реестре контента;
  - слоты рисуются прямоугольниками по размеру карты, всегда по осям `Graph`;
  - шаг сетки — множитель: по X — шаг × ширина карты, по Z — шаг × длина (гекс растягивается так
    же); шаг 1 — карты встык;
  - автоконнект и минимальный радиус — в размерах карты (смещение по X делится на ширину карты, по Z —
    на длину);
  - высота: одиночный слот — рейкастом по геометрии; у сетки настройка «высота рейкаста» — каждая
    клетка делает рейкаст вниз с y начальной точки + смещение (нет попадания — y начальной точки);
  - сетку можно двигать и вращать целиком (ручки в «Выборе»): вращение позиций вокруг центра
    сетки по оси Y, ориентация прямоугольников не меняется (скошенные сетки); сдвиг и поворот
    применяются к текущим позициям слотов, высоты пересчитываются рейкастом; ручная правка
    отдельных слотов после этого по-прежнему возможна.

#### Реализация (T070, T071, 2026-10-22)

- `FieldConfig` (`Code/Model/Graphs/`, `ContentAsset`, меню `[Game]/Field Config`) — `CardSize`
  (1,5 × 2); ассет `Content/Field/FieldConfig.asset`. Валидатор: больше одного — ошибка каждому;
  «нет ни одного» — только при полной проверке реестра проекта.
- Расстояние для минимального радиуса и автоконнекта: √((dx/w)² + dy² + (dz/l)²) — Y в локальных
  единицах без деления. По умолчанию: шаг 1,1 (зазоры 0,15 × 0,2), автоконнект 1,3 (соседи
  крестом), минимальный радиус 1, высота рейкаста 1, радиус кисти 2.
- Вертикальный рейкаст (`SceneGround`, Editor): `MeshRenderer` + `MeshFilter` (активные, видимые,
  выбираемые) — внутренний `HandleUtility.IntersectRayMesh` через рефлексию с проверкой сигнатуры,
  запасной путь — свой перебор треугольников (читаемые меши); `Terrain` — `SampleHeight`, если
  ось Y графа смотрит вверх. `SkinnedMeshRenderer` не учитывается. Луч — по −Y `Graph`.
- Сетка хранит `From` / `To` (прямоугольник до поворота, сдвигается с сеткой), `Angle`
  (градусы, [−180, 180)), `RaycastHeight`; центр поворота — середина прямоугольника на высоте
  `From.y`. Сдвиг и поворот — к текущим позициям слотов, высоты — лучом с `From.y` + высота
  рейкаста; нарушение минимального радиуса относительно слотов вне сетки отклоняет операцию.
  Ручки: `PositionHandle` по осям `Graph` и `Handles.Disc` вокруг Y со снапом; одно перетаскивание —
  один шаг Undo.
- Выбор под мышью: центр слота (12 px) → связь (6 px, в Select) → прямоугольник карты.
- Кисть: слоты с центром в круге по XZ (граница включена); добавить можно только объявленный тег;
  Shift проверяется на каждом событии; протягивание — один шаг Undo (`CollapseUndoOperations`);
  радиус 0–20.
- Гекс при шаге меньше 2/√3 ≈ 1,155 даёт перекрытие прямоугольников соседних рядов по Z.

### Экспедиция в модели слотов

- Старт: создаются слоты экспедиции, колода экспедиции наполняется из `DeckModel`, герой и
  способности **перемещаются** (не копируются) из слотов хаба в слоты экспедиции.
- Ход: действия игрока и реакции карт двигают карты между слотами поля.
- Конец: успех — содержимое рюкзака переносится в колоды хаба, неистраченные способности
  возвращаются; провал — рюкзак теряется (см. «Ход экспедиции»). Слоты экспедиции уничтожаются.
- Состояние экспедиции сохраняется: слоты поля, состояния карт, счётчик ходов, номер хода,
  состояние `Rng`. Сохранение — только когда нет активных скриптов.

#### Ход экспедиции (решено 2026-11-04, T076)

- Шаг 7 E03 разбит на две задачи: T076 — ход в модели (старт, действие игрока, конец хода, монстры, счётчик,
  конец экспедиции, тест без сцены); T077 — старт и конец через `GameFlow` (запрос старта, сцена, возврат в хаб).
- `ExpeditionSystem` (секция `expedition`): старт (слоты экспедиции, герой и способности, раскладка; повторный
  старт — ошибка до изменений), действие игрока, конец хода, конец экспедиции.
- **Действие игрока**: взять можно героя на поле и карту из руки — лицом вверх, `AllowedMoves` не пуст; положить —
  только на слот из `AllowedMoves`, иначе отмена без событий (клетки героя в `AllowedMoves` нет — возврат на неё
  не ход, T046). Перетаскивание — всегда с хуками. Действие вместе с концом хода — одна активность: сохранение
  ждёт его конца.
- **Конец хода решает скрипт** — команда `end turn`: герой вызывает её в `OnPlaced`, способность — по решению
  дизайнера. Обработка — после завершения действия, не вложенно: `OnStep` у верхней карты каждой клетки поля
  (список фиксируется до начала, порядок — слоты графа, карта, ушедшая с поля, пропускается, каждая карта —
  один раз), затем номер хода +1. Пропуск хода (T047) — конец хода без действия.
- **Счётчик ходов** — встроенный, в сейве: `turns left`, `set turns left to [N]`, `add [N] to turns left`. Меняют
  его только скрипты (пересмотрено 2026-11-04): тратит ли действие ход, решает скрипт действия. Ход героя — общий
  `Cards.HeroStep`, как `PlayerStep` прототипа: ходов ≤ 0 — поражение, под героем выход — победа, иначе
  `add -1 to turns left` и `end turn`. Revolver — только `end turn` (ход монстров без траты хода, как в прототипе).
  Номер хода растёт сам в конце хода (`turn number`).
- **Поражение от карты** (2026-11-04): объявляет скрипт, который убирает героя с поля (как `Explosives` прототипа),
  не хук героя — в колоде, рюкзаке и сбросе хуки размещения не вызываются.
- **Конец экспедиции** — `end expedition with victory` / `end expedition with defeat`: текущий скрипт
  выполняется до конца, остаток хода (монстры, номер хода) пропускается, затем событие для сюжета. Текст экрана
  итогов — вместе с UI (E06).
- **Итоги**: победа — рюкзак уходит в инвентарь хаба; поражение — рюкзак теряется. В обоих случаях герой и
  способности возвращаются в инвентарь, где бы ни лежали (в том числе из рюкзака); остальные карты экспедиции
  уничтожаются вместе со слотами. Заряды при возврате не восстанавливаются. Запоминание выбора для экрана
  подготовки — открытый вопрос (T077).
- **Перемещение командой**: `move [Card] to [Slot]` — с хуками размещения, `move [Card] to [Slot] without hooks` —
  без хуков (как `RaiseEvents=false` в прототипе). Teleport: карта под способностью — без хуков, герой — с
  хуками (ход заканчивается через `OnPlaced` героя).
- **Переменные экспедиции** (решено 2026-11-04) — область `Expedition` (см. «Переменные»): сброс при старте, сейв
  вместе с экспедицией, удаление в конце. Счётчик ходов остаётся встроенным.

  `SkipTurn()` (`UniTask<bool>`); состояние — `IsActive`, `Slots`, `Location`, `TurnsLeft`, `TurnNumber`, `CanAct`, `IsActing`,
  `Variables` (`IExpeditionVariables`); событие `Ended` и `ExpeditionEnded(location, result)` в `EventBus`. Для узлов —
  `TryRequestEndTurn`, `TryRequestEnd(result)` (отказ — текст причины), `SetTurnsLeft`, `AddTurnsLeft` (вне экспедиции —
  исключение; узлы проверяют сами и пишут предупреждение).
- Старт: проверки до изменений (экспедиция идёт или её слоты есть, герой не живая карта, у локации нет поля) →
  `CreateExpedition` → экспедиция идёт, ход 1, счётчик 0, переменные экспедиции по умолчанию → `DealSystem.Deal`. Проверки
  раскладки (способности, клетка `PlayerSpawn`) отказывают синхронно при пустых слотах экспедиции — тогда слоты удаляются и
  состояние прежнее. Нет колоды — предупреждение `[Expedition]`, раскладывается только герой; валидатор — предупреждение
  `InvalidDeal` у локации типа `Expedition` с полем без колоды. Старт — не действие игрока: `end turn` / `end expedition` в
  `OnPlacedFirstTime` не принимаются.
- Действие принимается при `CanAct`: экспедиция идёт, нет действия и активных запусков исполнителя (`ActiveCount == 0` — любой
  запуск, в том числе диалог, ждущий игрока). Взять: герой экспедиции на клетке поля или карта руки — живая, лицом вверх.
  `GetAllowedMoves` — `AllowedMoves` без собственного слота карты и без слотов, которые её не примут (`SlotSystem.CanMove`).
  `Play` — `CardSystem.Move` с хуками без контекста: хук каждой карты — отдельный запуск, ошибка в нём не прерывает действие.
- Одна активность: действие или пропуск, конец хода и итоги — один `ScriptRunner.RunCode("expedition <локация>: ...")`.
- Конец хода: верхние карты клеток (`Field.Cells`, порядок графа) фиксируются списком; по очереди: итог уже запрошен — стоп;
  карта уничтожена или не на клетке поля — пропуск; иначе `OnStep` отдельным запуском. Затем `TurnNumber` + 1 (`TurnsLeft` конец
  хода не меняет — только скрипты, 2026-11-04). Итог запрошен в действии — конец хода не начинается; в `OnStep` — оставшиеся
  `OnStep` и номер хода пропускаются; затем итоги.
- Итоги: в инвентарь — герой экспедиции, карты с `AbilityCard` из всех слотов экспедиции (порядок `ExpeditionSlots.All`:
  колода, рука, сброс, рюкзак, клетки, связи), при победе — остаток рюкзака; `SlotSystem.Move` без хуков, сторона карты — как
  лежала. Инвентарь не принимает (ёмкость) — предупреждение, карта теряется с экспедицией. Затем `DestroyExpedition`, ход и
  счётчик — 0, переменные экспедиции удаляются, `Ended`, `ExpeditionEnded`.
- Запросы скриптов вне экспедиции или вне действия игрока (раскладка, фоновый запуск после действия) — предупреждение и ничего;
  повторный `end turn` и `end turn` во время `OnStep` — тот же конец хода, без предупреждения; повторный `end expedition` — первый
  итог остаётся, предупреждение.
- Сейв `expedition` (`LoadOrder` 30, после `slots`), версия 1: `{active, turnsLeft, turnNumber, variables: {имя: значение}}` —
  переменные только явно заданные. Запросов в сейве нет: сохранение только без действия. `active`, а слотов экспедиции нет
  (локация пропала) — предупреждение, экспедиции нет; слоты экспедиции при `active: false` (сейвы до T076, тесты) — без
  предупреждения, экспедиция не идёт.
- Контент: герои (`Content/Entities/Heroes/`) — `set turns left to 25` в `OnPlacedFirstTime` (у Alfredo и Stefan прототип брал
  25 из `LocationModel.Steps`); `OnPlaced` Lucia и Stefan — раскрытие и `call Cards.HeroStep` (`Content/Scripts/Cards.script`);
  Alfredo (обучение) — та же логика своим текстом, на выходе победа (диалоги и монеты `PlayerStep_Tutorial` — E12). Монстр съел героя — поражение. Talisman — `add 3 to turns left` (без конца хода, как в
  прототипе), Revolver — `end turn` после выстрела, Teleport — карта под ним `without hooks`. Комментарии про камеру — E06.
- Заглушка шага 5 `Content/Entities/Hero.asset` + `Hero.script` удалена; тестовый герой с прежним скриптом — `CardTestKit.Hero`
  (`HeroScript`), `CardContentTests` — на Lucia (поле 3 × 3 с шагом 1,5 × 2).
- Отличия от предложения: номер первого хода — 1 (вне экспедиции 0); запросы вне действия игрока отклоняются; `CanAct` учитывает
  любой активный запуск, а не `IsIdle`. По итогам ревью (2026-11-04): счётчик ходов меняют только скрипты (`Cards.HeroStep`),

#### Колода и начальная раскладка (решено 2026-10-22, T072)

- **Колода — основная абстракция.** Инвентарь игрока — колода. Локация экспедиции = колода + граф +
  визуальное оформление (сцена).
- Колода экспедиции — конфиг, на который ссылается локация: строки «модель карты + количество».
  У строки — галка **«не раскладывать»**: такие карты при старте остаются в колоде (для скриптов,
  T016). Галка на строке колоды, не на модели карты.
- **ГСЧ сессии** (решено 2026-11-04, T072): один на сессию, свой алгоритм (не `UnityEngine.Random` —
  глобальное состояние, не сохраняется), состояние в сейве (секция `rng`), поэтому перезагрузка исход не
  меняет; seed при новой игре случайный, в тестах фиксированный. Узлы: `random card of [Cards]`,
  `random slot of [Slots]`, `random number from [A] to [B]`, условие `chance [N]%`.
- Герой до шага 6 E03: раскладка получает карту героя параметром, кладёт её на `PlayerSpawn` и ставит
  ссылку экспедиции на героя.
- Раскладка — одна карта на слот, случайно (ГСЧ сессии, состояние сохраняется, в тестах
  повторяемо):
  1. карты с `SpawnSlot` — первыми: свойство в файле карты возвращает **набор** допустимых
     слотов (`SpawnSlot -> [slots tagged Exit]`), карта занимает случайный свободный из набора;
     свободного нет — карта остаётся в колоде, валидатор предупреждает;
  2. остальные карты — в случайные из оставшихся слотов; слоты `PlayerSpawn` пропускаются;
  3. герой — последним, в слот с тегом `PlayerSpawn` (несколько — случайный, ни одного — ошибка
     валидатора); способности — в руку.
- Карт меньше, чем слотов, — лишние слоты пустые; больше — остаток в колоде.
- `OnPlacedFirstTime` — отдельным циклом после раздачи, в порядке раздачи, у героя последним
  (реакции не видят наполовину заполненное поле; у карт может быть особая логика).
- Раздача — скрипт с анимацией; во время неё сохраняться нельзя. Переворот карт вокруг героя и
  поведение карт — хуки и правила хода, не раскладка.

##### Реализация (T072, 2026-11-04)

- ГСЧ — `Code/Core/Rng/`: `Xoshiro128` (xoshiro128** 1.1, состояние — четыре `uint`, seed 64 бита разворачивается
  SplitMix64; только целочисленная арифметика — одинаково на всех платформах), `Range(min, max)` включительно без смещения
  (отбрасывание значений ниже 2³² mod n). `RngSystem` — система сессии (Core, регистрирует `SessionBuilder`), секция `rng`
  `{state: [4 числа]}`; неверное состояние — предупреждение и seed новой игры. Seed новой игры — `RngSystem.NewGameSeed`
  (задаётся в `configure` `Session.Create`, в тестах фиксированный); null — из `Guid.NewGuid` (есть и в Web). `Chance(N)` всегда
  берёт одно число 0..99 — смена шанса не сдвигает остальные результаты.
- Колода — `DeckModel` (`Code/Model/Decks/`, `ContentAsset`, меню `[Game]/Deck`): строки `DeckEntry` — конфиг
  (`[ModelKind(Card)]`), количество, «не раскладывать» (`KeepInDeck`). `LocationModel.Deck`; null — раскладывается только
  герой. Пример — `Content/Decks/TestLocationDeck.asset` (выход, монстры, травы, 4 травы «не раскладывать»).
- Раскладка — `DealSystem.Deal(hero)` (система сессии без состояния, асинхронно): экспедиция уже создана, герой — живая
  карта в любом слоте. Порядок: колода наполняется строками (создание в `exp/deck`, рубашкой) → перемешивание Фишера — Йетса
  ГСЧ сессии → клетка героя (случайная свободная `PlayerSpawn`) выбирается сразу и для других карт занята → карты со
  свойством `SpawnSlot` по порядку колоды сверху вниз: случайная свободная клетка поля из набора (слоты набора не на поле не
  учитываются; свободной нет — предупреждение `[Deal]`, карта в колоде; ошибка вычисления — то же) → остальные — в случайные
  свободные клетки без `PlayerSpawn` → герой (лицом вверх, `SetHero`) → `OnPlacedFirstTime` в порядке раздачи, герой
  последним. Нет экспедиции, герой не живая карта, нет свободной `PlayerSpawn` — `InvalidOperationException` до изменений.
  Свободная клетка — пустая.
- Способности (T075): `Deal(hero, abilities)` (второй параметр необязателен, null — без способностей). Способности
  перемещаются (не копируются) в руку экспедиции в переданном порядке, лицом вверх — после героя и `SetHero`, до цикла
  `OnPlacedFirstTime`: хуки уже видят их в руке; своего `OnPlacedFirstTime` у них нет (рука — не клетка поля). Ошибка до
  любых изменений (`InvalidOperationException`): способность не живая карта, повторяется, это сам герой, нет компонента
  способности, не подходит герою (`AbilityCard.Fits`), способностей больше места в руке (ёмкость минус карты в ней), правила
  руки не пускают. Проверки способностей — после проверки героя, до проверки клетки `PlayerSpawn`.
- Раздача — один запуск `ScriptRunner.RunCode` (Core, 2026-11-04): запуск кода C#, зарегистрированный как запуск секции;
  пока он идёт, `IsIdle` = false и `BecameIdle` не срабатывает между хуками; исключения кода, включая отмену, уходят
  вызывающему. Хук каждой карты — отдельный запуск (`CardSystem.InvokeHook` без контекста): ошибка в хуке одной карты не
  прерывает раскладку, лимит шагов у каждого хука свой.
- Валидатор контента (`Code/Editor/Decks/DeckChecks.cs`): строка колоды без конфига или с количеством меньше 1 —
  `InvalidDeck`; у локации с колодой нет поля или клетки `PlayerSpawn` — `InvalidDeal`; предупреждения `InvalidDeal`
  (`ContentError.IsWarning`, билд не останавливают) — первый шаг раскладки на пустом поле в сессии без сцены: каждая карта
  строк без «не раскладывать» вычисляет `SpawnSlot` и занимает первую свободную клетку (клетка героя — первая `PlayerSpawn`);
  кому не хватило — предупреждение. Только для контента без ошибок (иначе ошибки объявлений попали бы в лог повторно); файлы
  с ошибками разбора пропускаются.
- Тесты: `Tests/EditMode/Rng/RngTests.cs` (эталонные последовательности посчитаны независимой реализацией),
  `Tests/EditMode/Decks/` (раскладка и валидатор), `Tests/EditMode/Cards/RandomNodeTests.cs`.

## Сохранения

### По слоям (подтверждено 2026-10-11)

| Слой | Что делает |
|---|---|
| Core | ядро сохранений: API слотов (список, сохранить, загрузить, удалить), `SaveGame` (meta + секции), упаковка в zip, атомарная запись через интерфейс хранилища, `ISaveable`, миграции, ротация 3 автосейвов |
| Model | системы реализуют `ISaveable`, у каждой своя секция-DTO |
| Game | когда сохранять: `GameFlow.CanSave` (нет перехода и активных скриптов, кроме диалога, ждущего игрока), автосейв по таймеру и при выходе; загрузка = `CreateSession(save)` |
| UI | экран слотов через VM, список по `meta.json` |
| Integrations | хранилище: файлы (PC, мобильные), Web; облако Steam — по необходимости |

Настройки игрока хранятся отдельно от слотов.

### Формат

- Один слот = один zip-архив: `saves/<slotId>.tgsave`.
- Внутри: `meta.json` + по файлу на секцию (`cards.json`, `slots.json`, `story.json`, ...) +
  `thumbnail.png` (скриншот для списка слотов).
- `meta.json`: версия формата, версия игры, дата, время в игре, название шага сюжета и локации,
  тип слота (manual/auto). Список слотов строится по `meta.json` без чтения остального.
- Запись атомарная: во временный файл, затем замена.
- Ядро сохранений (Core) работает через интерфейс хранилища. Реализации под платформы — модули-
  интеграции: файлы (PC, мобильные), Web (хранилище браузера). Подключаются в Game.
- Сериализатор DTO — Newtonsoft (уже в проекте), без `TypeNameHandling`. Полиморфизм в DTO —
  только через явный строковый дискриминатор (ключ компонента), никогда через имена .NET-типов.

### Слоты

- Ручные сохранения: без ограничения количества (ветвления сюжета — игроку важно пробовать
  разные выборы без переигрывания).
- Автосейвы: 3 слота по кругу, перезаписывается самый старый (по дате в `meta.json`).
- Автосейв (пересмотрено 2026-11-04, T077): в коде — по таймеру (интервал в конфиге, как в прототипе — 5 минут)
  и при выходе в меню и из игры; по игровым событиям (вход в хаб, смена шага, конец экспедиции, конец хода) —
  скриптами: событие + команда `autosave`. Только при `GameFlow.CanSave` (см. architecture-flow.md).
- В диалоге — только когда он ждёт игрока (решено 2026-10-17). Команда `autosave` разрешена в любых скриптах
  (2026-11-04; было — только в диалогах).

### ISaveable

Аналог `ISaveEntity` из GeekyHouse. Отличия:

| GeekyHouse `ISaveEntity`                            | TheGrowth `ISaveable`                                                            |
| --------------------------------------------------- | -------------------------------------------------------------------------------- |
| `Load()` сам тянет данные из `SaveManager.Get<T>()` | `Read(section)` получает секцию от сессии (push)                                 |
| `Dirty`, `SaveAllowed` на каждом менеджере          | нет; сохранение только в точках сохранения, разрешение одно — `GameFlow.CanSave` |
| один глобальный сейв, загрузка один раз при старте  | слоты; `Read` вызывается при каждом создании сессии                              |
| файл на менеджер, неатомарно                        | секция = файл внутри одного zip, запись атомарная                                |
| версии нет                                          | версия на секцию + миграции                                                      |

```csharp
public interface ISaveable
{
    string SaveKey { get; }     // стабильный ключ секции: "cards", "slots", ...
    int SaveVersion { get; }    // текущая версия схемы секции
    int LoadOrder { get; }      // cards раньше slots, slots раньше expedition
    object Write();             // вернуть DTO секции
    void Read(SaveSection section);  // section == null → новая игра, значения по умолчанию
}

public abstract class SaveableSystem<TSave> : SharedObject, ISaveable where TSave : class, new()
{
    public abstract string SaveKey { get; }
    public virtual int SaveVersion => 1;
    public virtual int LoadOrder => 0;

    object ISaveable.Write() => Write();

    void ISaveable.Read(SaveSection section)
    {
        if (section == null)
        {
            ReadDefaults();
            return;
        }

        Read(section.Get<TSave>(SaveVersion));   // внутри — миграции до текущей версии
    }

    protected abstract TSave Write();
    protected abstract void Read(TSave save);
    protected virtual void ReadDefaults() { }
}
```

- `ISessionReady.OnSessionReady()` вызывается после `Read` всех систем — для связей между
  системами (слот ссылается на `InstanceId` карты из `CardRegistry`).

### Миграции

- Версия на секцию. Миграция — функция над JSON/DTO секции `vN → vN+1`, регистрируется
  в `SaveMigrations`. Цепочка применяется при чтении.
- Миграции работают с данными, а не с игровыми классами — переименование кода на них не влияет.
- Тест на каждую миграцию: фикстура старого сейва → чтение → проверка состояния.

### Реализация (T065, 2026-10-19)

Код: `Code/Core/Saves/`, `Code/Integrations/SaveFiles/` (`SaveFileStorage`), `Code/Model/Locations/`
(`LocationSystem`), `Code/Game/Flow/Requests/` (`SaveGameRequest`, `LoadGameRequest`), `Code/Game/Saves/`
(`SaveThumbnail`).

- Секция в архиве — `<key>.json` вида `{version, data}`; данные секции — `JObject`. JSON: Newtonsoft
  без `TypeNameHandling`, camelCase (ключи словарей как есть), enum строкой, даты UTC.
- `ISaveStorage` — асинхронный API (UniTask): чтение отдаёт поток с поиском, запись —
  `WriteAsync(id, Action<Stream>)`, атомарная. Список слотов: `ZipArchive` читает центральный
  каталог и одну запись `meta.json`.
- Файлы: `persistentDataPath/saves/<id>.tgsave` (папка общая с файлами прототипа — не меняем,
  хранилище читает только `.tgsave`); запись в `<id>.tgsave.tmp` → `Flush(true)` →
  `File.Replace` (новый слот — `File.Move`). Ввод-вывод синхронный в главном потоке, пул
  потоков не используется (Web).
- ID слотов `[a-z0-9_-]`: ручные `manual_yyyyMMdd_HHmmss` (UTC, при совпадении `_2`, `_3`, ...),
  автосейвы `auto_1..3`; перезаписывается пустой или битый, иначе самый старый по `savedAtUtc`.
- `SaveService` (глобальная область) исполняет операции строго по одной; `WaitIdleAsync` —
  ожидание конца записи (выход из приложения).
- Миграции регистрирует сама система (`SaveableSystem.RegisterMigrations`), глобального реестра
  нет. Применяются к копии данных; следующее сохранение пишет текущую версию.
- Сессия: `Session.Create(parent, SaveGame, configure)`; `Session.Capture()` собирает секции.
  Секция без системы — предупреждение; один ключ у двух систем — исключение.
- `LocationSystem` — секция `locations` (текущая локация). Локации из сейва нет в контенте —
  предупреждение, вход в `GameConfig.StartLocation`, остальное состояние сохраняется.
- Время в игре — в Game: `meta.playTimeSeconds` + реальное время с создания сессии; пауза и
  свёрнутое приложение не вычитаются.
- Превью — камеры экрана рендерятся в текстуру шириной 320 px → PNG; UI в снимок не попадает.
  Чтение превью для списка — `SaveService.LoadThumbnailAsync` (T067).
- Виды ошибок (T067): `SaveException.Kind` — `SaveErrorKind` (Unknown, NotFound, Corrupted,
  NewerVersion, MissingMigration); по нему UI выбирает текст для игрока.

## Диалоги и переменные

## Переменные (решено 2026-10-17, T052)

Единая система дизайнерских переменных — общая для скриптов карт и диалогов. В прототипе
переменных не было (только `Charges`).

| Область | Где живёт | Сохраняется | Примеры |
|---|---|---|---|
| Игра | `VariablesSystem` сессии | секция `variables` слота | доверие персонажей, имя игрока, развилки сюжета |
| Карта | экземпляр карты | вместе с картой | заряды, счётчик ходов эффекта |
| Профиль | глобально, вне слотов | рядом с настройками игрока | открытые концовки, галерея |
| Экспедиция | `ExpeditionSystem` сессии, пока идёт экспедиция | секция `expedition` слота; при старте — по умолчанию, в конце удаляются | найденные подсказки, флаги событий экспедиции |

- Переменные объявляются заранее в геймдизайнерских конфигах: имя, тип, значение по умолчанию,
  описание. Конфигов может быть несколько по темам. Переменные карты — списком на модели карты
  (T042).
- Типы: `bool`, `int`, `string`.
- Переменные карт: имена объявляются один раз в общем реестре (имя, тип); модель карты выбирает
  из реестра и задаёт значения по умолчанию. Парсер проверяет `[карта].имя` по реестру. Чтение
  отсутствующей у карты переменной — значение по умолчанию из реестра; запись — ошибка с местом в
  скрипте.
- Синтаксис: `$имя` — переменная игры, профиля или экспедиции (область — из объявления), `[карта].имя` —
  переменная карты, где `[карта]` — эвалуатор карты. Парсер проверяет существование и тип.
- Хранилище и ссылки на переменные — Core (часть языка). Изменение — событие в `EventBus`
  (UI, квесты, триггеры сюжета).
- Имя переменной — стабильный ID. Переименование — миграция сейва или список прежних имён в
  объявлении; скрипты со старым именем находит валидатор.

### Реализация (T052, 2026-10-21)

Код: `Code/Core/Variables/`, `Code/Core/Profile/`, `Code/Model/Variables/`,
`Code/Integrations/SaveFiles/` (`ProfileFileStorage`, `AtomicFile`). Пример объявлений —
`Content/Variables/Variables.asset` (меню создания `[Game]/Variables`).

- Объявление — `VariableDeclaration` в списке конфига `VariableDeclarations` (`ContentAsset`): имя,
  область (`Game` / `Card` / `Profile`), тип (`Bool` / `Int` / `String`), значение по умолчанию
  строкой (`true` / `false`, целое, строка как есть; пусто — `false` / `0` / `""`), описание,
  прежние имена. Имена уникальны по всем конфигам и областям, прежние имена не совпадают ни с
  текущими, ни друг с другом; при дубле действует первое объявление.
- `VariableCatalog` — глобальный сервис, собирается из реестра контента; ошибки объявлений — в лог
  при `Init` и в валидатор контента (`ContentErrorKind.InvalidVariable`).
- `VariableStore` — одно хранилище на все области, проверка типа; событие `VariableChanged` —
  только при реальном изменении: сначала `VariableStore.Changed`, затем `EventBus`.
- Владелец переменных — `IVariableOwner` (будущий `CardInstance`, E03); `IGameVariables`,
  `IProfileVariables`.
- Игра — `VariablesSystem` (Model, `SessionBuilder`), секция `variables` версии 1:
  `{"values": {...}}` — только явно заданные значения (новое значение по умолчанию применяется к
  старым сейвам). Необъявленное значение, другой тип или область — предупреждение и значение по
  умолчанию; значение под прежним именем читается под новым, при обоих — остаётся текущее.
- Профиль — `ProfileService` (Core, глобальная область): читается при `Init`, пишется целиком сразу
  при каждом изменении, синхронно и атомарно. Файл `persistentDataPath/profile.json`,
  `{"version": 1, "variables": {...}}`. Ошибка записи — лог, игра продолжается.
- Защита профиля (2026-10-21): нечитаемый профиль копируется рядом (`IProfileStorage.KeepCopy`,
  `profile.unreadable-<дата UTC>.json`), затем значения по умолчанию. Профиль более новой версии
  игры и нечитаемый профиль, копию которого сделать не удалось, не перезаписываются
  (`ProfileService.IsReadOnly`): изменения работают в этой сессии, но не пишутся.
- Импортёр скриптов разбирает переменные по объявлениям; зависимость `TheGrowth/Variables`
  (хеш имён, областей, типов и прежних имён — без значений по умолчанию).
- Экспедиция (T076, 2026-11-04) — область `VariableScope.Expedition`, в скриптах `$имя` (нового синтаксиса нет; `[карта].имя` —
  ошибка разбора, как у игры и профиля). Хранилище — `IExpeditionVariables.Variables` (`ExpeditionSystem`): `null`, пока
  экспедиция не идёт; тогда чтение — значение по умолчанию из объявления, запись (`set`, `add`) ничего не делает, оба — с
  предупреждением `[Variables]` (запуск, переменная). При старте — значения по умолчанию, в конце удаляются (без событий); в сейве
  — `variables` секции `expedition`, только явно заданные. События — как у остальных областей. У карты переменная экспедиции
  быть не может — ошибка схемы сущности (как у других областей).
